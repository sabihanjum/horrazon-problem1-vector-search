## What This Project Does

This project implements a **metadata-filtered approximate nearest-neighbour (ANN) search system** from scratch — without FAISS, hnswlib, Annoy, ScaNN, or any library that provides the search index itself.

The motivating scenario is an e-commerce catalogue (think: Tamil Nadu fashion products) where every search must respect product metadata: category, delivery zone, and price range. Three different search strategies are implemented, a query planner chooses among them based on estimated selectivity, and a full benchmark validates correctness against brute-force ground truth.

---

## Key Design Decisions

### Why hand-rolled IVF?

Standard ANN libraries pre-filter or post-filter uniformly — they don't let you choose dynamically. Building IVF from scratch means the strategy can be swapped at query time based on how many products a filter is expected to match.

### Why three strategies instead of one?

| Scenario | Problem | Best strategy |
|---|---|---|
| Filter matches >5% of products | Post-filtering throws away too many candidates | Exact scan (no approximation loss) |
| Filter matches 0.5%–5% | Neither pure pre nor pure post is optimal | Partition-then-filter: probe enough partitions, discard after |
| Filter matches <0.5% | Most products are irrelevant; scanning all costs more than the query saves | Filter-aware partition search: stop probing when enough pass the filter |

### Why MiniBatchKMeans for partitioning?

The problem statement permits a k-means library for creating partitions. MiniBatchKMeans from scikit-learn is fast enough to cluster 50,000 128-dim vectors in ~23 seconds on a CPU. The resulting partition structure is purely used as a static inverted list — all search logic is hand-written.

### Why independence assumption in the stats model?

The stats model estimates selectivity as:  
`P(cat) × P(zone) × P(price range)`

This is deliberately simple. When category and price are correlated (e.g., *kanjivaram* sarees are never priced under Rs. 1,000), the model over-estimates and can make a suboptimal planner decision. This is the **known failure mode** tested in `test_planner_failure.py`.

The fix — storing per-category price histograms — is described in the test but deliberately not implemented, to preserve the documented failure case.

| Property | Value |
|---|---|

| Vector dimension | 128 |
| Categories | 20 (saree, silk_saree, kurta, kanjivaram, …) |
| Delivery zones | 30 Tamil Nadu cities (Madurai, Chennai, Coimbatore, …) |
| Price range | Rs. 150 – Rs. 25,000 (log-normal distribution) |
| Vector structure | Clustered (30 latent centres + Gaussian noise) |

The clustering in the vector space means the IVF partitions are meaningful — related products genuinely end up in nearby partitions. This makes the recall/latency tradeoff more realistic than pure random vectors.

## Search Strategies

### Strategy A — Exact Scan (`exact_scan`)
Used when filter selectivity ≥ 5%. Scores ALL products that pass the filter. O(N·sel) distance computations, but zero recall loss. This is the "safe" baseline.

### Strategy B — Partition-then-Filter (`partition_then_filter`)
Used when filter selectivity is between 0.5% and 5%. Probes the nearest `nprobe` IVF partitions (selected by centroid distance to the query), collects all candidates from those partitions, then applies the metadata filter as a post-processing step. `nprobe` scales inversely with selectivity so that lower-selectivity queries probe more partitions to compensate.

### Strategy C — Filter-Aware Partition Search (`filter_aware_partition_search`)
Used when filter selectivity < 0.5%. Probes partitions in order of centroid distance, but tracks how many filtered candidates have been accumulated. Stops early once `min_candidates` qualified products are found. This avoids scanning partitions that are unlikely to contribute matching products.

---

## Planner

```
selectivity >= 5%         ->  exact_scan
0.5% <= selectivity < 5%  ->  partition_then_filter
selectivity < 0.5%        ->  filter_aware_partition_search
```

`nprobe` is scaled: `nprobe = max(4, min(K, round(nprobe_base / max(sel, 0.001))))`  
At very low selectivity the planner probes many more partitions to preserve recall.

**Recall@10 ≥ 0.95 across all 5 selectivity groups.**

This is verified by:
- `tests/test_recall.py` (CI, 10,000-product fixture, 20 queries per group)
- `benchmarks/benchmark.py` (full 50,000-product run, 30–50 queries per group)

## Known Limitation (Documented Failure)

**Test:** `tests/test_planner_failure.py::test_planner_failure_case`

**Scenario:** Filter `category=kanjivaram AND price=[0, 5000]`. All kanjivaram products cost ≥ Rs. 8,000 in the test dataset. The StatsModel assumes independence and estimates a positive count. The planner therefore chooses a sub-optimal strategy for a filter that matches 0 products.

**Root cause:** Joint probability `P(category=kanjivaram, price≤5000)` is 0, but `P(category=kanjivaram) × P(price≤5000) > 0`.

**Fix:** Store per-category price histograms in StatsModel so P(price | category) replaces the independence assumption.
